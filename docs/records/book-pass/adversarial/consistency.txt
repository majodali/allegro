# Consistency review of the decisions extract

Source read: `decisions-extract.md` only (D1–D216). Fifteen findings, strongest first.
Severity count: blocks 2, needs a ruling 11, wording 2.

### C1. An unevaluated argument evaluated "transformed" in the caller's context hands the callee everything the caller can name
- Decides: D57 (A function may take an argument unevaluated), D43 (A capability is granted, never acquired), D56 (The environment is not a value), D40 (Transient reference symbols resolved by base name), D119 (A private member is one whose key not all code holds), D181 (Only the launcher sets the ceiling)
- Scenario: module `M` is evaluated in a scope that holds `files` (D181: "by being evaluated in a scope that holds it"; D185). `M` calls a library function `log(msg)` and passes it no capability. `log` declares `msg` unevaluated. Per D57 it may hand the expression back "to be evaluated in that context, whole, in part or transformed". `log` discards the expression and builds a new one: a transient symbol with base name `files` (D40: a symbol is resolved by base name against the enclosing scope), or `files.write("/x", secret_key)`. It asks the kernel to evaluate that in the caller's context. The result is `M`'s `files` capability, or any private key `M` can name.
- Why they conflict: D43 says an extension "cannot obtain a capability it was not handed". D56 says no program can inspect an environment. D57's "transformed" evaluation in the caller's context is exactly a probe of that environment by name. The context is opaque as a value but fully usable as an oracle. D57 lets the callee withhold capabilities from the argument; nothing limits what the callee draws out.
- Severity: blocks
- Confidence: medium-high
- What reading dissolves it: "transformed" means only re-arranging nodes that the caller wrote; any node the callee constructs resolves in the callee's own scope. The text does not say so, and "with names rebound" suggests the callee does introduce names. A second way out: a call site marks an unevaluated argument visibly, so passing one is an explicit grant of the caller's scope. That is a ruling, not a reading.

### C2. A reader that cannot obtain an unforgeable value cannot rebuild the expression that holds it
- Decisions: D42 (Reading an expression never yields authority), D38 (Functions are data: params plus body), D20 (No interface limits optimization), D57 (A function may take an argument unevaluated), D197 (A law licenses a rewrite, and the rewritten program carries the law's strength), D51 (Every value keeps its origin), D68 (The kernel's primitives are pure and few)
- Scenario: `narrow = p => files.read(concat("/tmp/", p))`. An extension `E` receives `narrow` and nothing else. Per D38 and D68 it reads the body: an expression whose head is the `files.read` function value. (a) If `E` can take that head node and build `Expression(head, ["/etc/passwd"])`, it has obtained the wide capability, against D42. (b) If the kernel gives `E` only a stand-in ("sees which one it is and cannot obtain it"), then an optimiser of D20 or D197, or a D57 transformer, cannot build a rewritten expression that still calls `files.read`: inlining `narrow` at a call site, or rewriting `read(a); read(a)` by a law, needs to place the same head in a new expression. The same holds through D51: `origin of r`, for any result `r` of `narrow("a")`, is readable by any code (D49) and contains the head.
- Why they conflict: D42 needs read access without reuse. D20, D57 and D197 need read access with reuse ("functions over a program's expression, open to every extension"). The six primitive groups of D68 offer "building and reading structures and expressions" with no third mode between them.
- Severity: blocks
- Confidence: medium (D42 is open; the conflict is in the stated goal)
- What reading dissolves it: the kernel offers a rebuild operation that accepts a stand-in only at the position, and with the arguments, where it was read, or only inside an expression re-evaluated in the original context. That is a new kernel primitive D68 does not list, and it still forbids rewrites that change a capability's arguments, which D197 allows for capability laws.
- Related, weaker: D51 with D121 (Export marks the binding, and a module with no exports is open). `export digest = h(secret)`; `secret` is not exported. `origin of digest` is the expression `h(secret)` with the plain value of `secret` in it. D42 protects unforgeable values only, so the unexported data is reached, against D121's "what it does not hand out cannot be reached".

### C3. Search, proposal loops and parse recovery must test for a refutation and carry on; D71 forbids it
- Decisions: D71 (A refutation marks everything computed from it), D165 (Solving is proposing a value for an unknown, and the kernel checks it), D167 (Feasible is decided; best says how strongly it holds), D210 (A proposer answers with only the missing value), D87 (Parse failure reporting and recovery), D75 (Parsing is evaluation), D176 (Limits are step budgets), D10 (A paradigm is a library)
- Scenario: a model has a field of type `Positive` (D117: `Positive(-1)` is a refutation). A search routine written in Allegro (D10, D165: "a search routine") tries candidates `-1, 0, 1`. Building the model with `-1` yields a refuted value. To try `0`, the routine must observe that refutation and continue. D71: "No code can remove the mark, test for it and carry on". The same occurs in D210 ("keeps it only if the claim is decided, for a bounded number of attempts"), in D87 (a parser, which is Allegro code by D76, meets a failure that D75 calls a refutation and recovers to report more), and in D176 ("an evaluation with a budget is also available to code inside the kernel, for evaluating what it does not trust": the caller must read whether the inner evaluation was refuted).
- Why they conflict: every in-language checker of a candidate needs a boundary at which a refutation becomes an inspectable outcome. D71 states that no such boundary exists for any code, and D68 lists no primitive for one.
- Severity: needs a ruling
- Confidence: high
- What reading dissolves it: D71 applies within one evaluation; a nested evaluation (D176) is a boundary whose result is data about the inner evaluation, and the outer program is not "carrying on" from a refuted value. Then D71's sentence needs that exception, D68 needs the primitive, and D14/D72 need a rule for refutations inside a nested evaluation. The alternative reading (candidates are tested only by calling predicates, per D117) fails for any model whose constructors make claims.

### C4. An undeclared name is a refutation, and an unbound symbol is a residual
- Decisions: D71 (A refutation marks everything computed from it), D166 (A solver sees its problem unevaluated), D55 (Evaluation is total over unresolved information), D7 (Order of definition carries no meaning), D96 (Running a program is evaluating its main module with a configuration's capabilities), D72 (A refutation on a path that may be taken refutes the program)
- Scenario 1: `solve(2 * x == 10)` where nothing declares `x`. D166: "an unknown may be represented by an unbound symbol, and ordinary evaluation of an expression that holds one gives a residual". D71: "a name that nothing declares" makes the program wrong, and everything computed from it is refuted, irremovably.
- Scenario 2: at a prompt (D96: "a module whose text arrives one entry at a time"), entry 1 is `y = x + 1`, entry 2 is `x = 1`. In a module file this is legal by D7. At the prompt, when entry 1 is evaluated nothing declares `x`. D71 marks `y` refuted for good. D55 and D62 say an unresolved input gives a residual that is evaluated again when the value arrives.
- Why they conflict: the kernel is given no criterion to tell "nothing declares it" from "not yet supplied". The two cases get opposite, and in one case irreversible, outcomes.
- Severity: needs a ruling
- Confidence: high for scenario 1, medium for scenario 2
- What reading dissolves it: an undeclared name is a refutation only when a text is closed (end of module); a solver's unknown is always a declared empty cell that the solver binds before evaluating (D57 "names rebound"), never a truly unbound symbol. D166's "ordinary evaluation" wording then has to change, and the prompt needs a stated rule.

### C5. A module is evaluated once, yet it is a function of capabilities each loader supplies
- Decisions: D69 (What the kernel requires of an extension), D185 (A module is a function of the capabilities it declares), D43 (A capability is granted, never acquired), D182 (Startup, step by step), D145 (A capability has named parts and narrowed forms), D107 (Generics are memoized type constructors)
- Scenario: module `Store` declares that it needs `files`. Module `A` imports `Store` and supplies the whole `files`. Module `B` imports `Store` and supplies `files.read` narrowed to `/tmp`. D69: "An extension is evaluated once in a configuration, and everything that names it gets the same values." D185: it is "evaluated in a scope that holds those ... supplied by whoever loads it". D43: an extension receives a capability "only when the code using that extension passes it one".
- Why they conflict: evaluated once, `B` gets a `Store` holding `A`'s wider grant (authority leaks to `B`), or `A` gets `B`'s narrow one (depends on load order, against D7 and D63). Evaluated twice, the two `Store`s are different values, their types are physically distinct (D107), and D69 is false. D182 step 4 gives a third answer: the launcher hands each capability "to the code the configuration names", which is neither importer.
- Severity: needs a ruling
- Confidence: high
- What reading dissolves it: module-level capabilities come only from the configuration (D182), and "whoever loads it" means the loader acting for the configuration; importers pass capabilities only as function arguments. D43's "the code using that extension passes it one" then describes calls, not imports, and D185 needs rewording.

### C6. A private key cannot be read back into existence, but every residual can be saved and reloaded as plain interface calls
- Decisions: D119 (A private member is one whose key not all code holds), D41 (Authority is an unforgeable value), D189 (A phase hands its residual to the next), D191 (A saved program is a recorded sequence of interface calls), D195 (Saving is export to a target whose model is the kernel's interface), D192 (A saved program names what it needs by content hash), D35 (Symbols interned by FQN), D68 (The kernel's primitives are pure and few)
- Scenario: a check phase evaluates a module that defines a type with a private member. The residual holds the accessor functions, whose bodies hold the key. D189: the residual "can be saved, loaded and evaluated further". D191: the data form is "a record of calls on the kernel's interface, and can do nothing else". Loading the record must produce the key again. Anyone who can read the record can replay the calls that produce it and then keep it. D119: "A key cannot be written out and read back into existence." The same holds for a capability: the record "names each primitive function ... by a hash" (D192), so a loaded program gets an effectful primitive by naming its hash, against D41 "Nothing is granted by name".
- Why they conflict: an unforgeable value must have an identity that no sequence of public calls reproduces. A saved program is by definition such a sequence. Also unstated: none of D68's six primitive groups, and none of D174's constructors, mints an unforgeable value, and the one identity-bearing kind is interned by name (D35), so it is forgeable by anyone who knows the FQN.
- Severity: needs a ruling
- Confidence: medium-high
- What reading dissolves it: a key is unforgeable within one kernel instance only; a saved program is trusted with whatever it contains, as far as its builder (D199), and capabilities in a record resolve only against what the loader was granted. D119's sentence then needs "within a kernel", and the kernel needs a stated minting primitive.

### C7. A claim assumed at the inner recursive call is reported as decided on the body
- Decisions: D59 (A recursive call is evaluated once for each state of knowledge), D21 (Every result says how strongly it holds), D16 (The kernel trusts only what it has evaluated), D153 (Termination is a claim), D135 (A proof term is a proposal)
- Scenario: `f(n: Int): Int & _ > 100 => f(n)` with `partial` (D153: "`partial` makes no claim"). Evaluating the body with `n` unknown meets a call to `f` with the same knowledge. D59: the call stays residual and the return claim is "assumed at that inner call and decided on the body". The body's result is the inner call's result, which is assumed to be > 100, so the claim comes out true and is recorded as decided. The same shape gives `absurd(): Proof[1 == 2] => absurd()` a decided return claim.
- Why they conflict: D21: "A result that rests on a weaker result is itself reported at the weaker strength." D16: what rests on an assumption "says so". Under those, every claim about a recursive function is at best assumed. Under D59 it is decided. When the function is not known to terminate, the decided claim is only partial correctness, and D21 defines decided as "the kernel evaluated it in full".
- Severity: needs a ruling
- Confidence: high on the strength labelling; medium on the unsound use (it depends on whether a residual `absurd()` can be used as a `by` term)
- What reading dissolves it: the inner assumption is an induction hypothesis, not an "assumed" result in D21's sense, and D59's result is decided only together with a decided termination claim; without one it is reported as assumed or conditional. Neither D59 nor D153 says this.

### C8. A claim decided through a primitive whose purity is assumed is both "decided" and resting on an assumption
- Decisions: D16 (The kernel trusts only what it has evaluated), D46 (Machine arithmetic is a set of pure primitives that ships with the platform), D21 (Every result says how strongly it holds), D19 (Host code reaches a program only as primitive functions), D204 (A primitive's purity is assumed and named unless something stronger is shown), D207 (A module's summary is the weakest strength among its claims)
- Scenario: `verify 2 + 2 == 4`. The sum is computed by a host primitive. D46 and D16: the claim "is decided, and names" the primitive. D19: the primitive's purity "is declared and assumed". D204: "a pure primitive is taken as pure on its declaration". D16 also says "a result the kernel did not evaluate itself is never reported as decided", and the host body is not evaluated by the kernel. D21: a result resting on a weaker result is reported at the weaker strength.
- Why they conflict: by D21 plus D19, every claim that touches `Int` arithmetic is assumed, so D207's summary for nearly every module is "assumed" and the word decided is almost never earned. By D16 and D46 the same claims are decided. Both readings are stated.
- Severity: needs a ruling
- Confidence: high that the text supports both
- What reading dissolves it: strength and "what it rests on" are two separate axes: a trusted primitive (D199) lowers nothing and is only named. Then D21's weakest-link sentence must exclude the trusted base, and D204's "three things are stronger" needs a place on some scale other than the four strengths.

### C9. A refutation in a branch the kernel could not rule out refutes the program, though undecidability and limits must never refute
- Decisions: D72 (A refutation on a path that may be taken refutes the program), D13 (Claims are evaluated like everything else), D74 (Evaluation stops early for two reasons only), D176 (Limits are step budgets), D149 (A match where no arm matches is a refutation), D112 (Abstract domains as sound approximations)
- Scenario 1: `if expensive(k) then ok() else assert(false)`, `k` known, `expensive(k)` in fact true. The step budget (D176) runs out inside `expensive(k)`. The condition is undecided, both branches are evaluated (D60), the else branch holds a refuted claim, and D72 refutes the program. D74: "A claim whose evaluation hits a limit is left undecided, not refuted." D13: "A claim is never reported as refuted because it could not be decided." The same occurs with any opaque predicate (D112: "No search runs") as the condition.
- Scenario 2: `when x is 0 then "zero"` with `x` an input of no known type. The fall-through arm is a refutation on a path that may be taken, so D72 refutes. D149, which depends on D72, says "Where the subject's possible values are not known, the claim is undecided."
- Why they conflict: D72 turns "could not decide the condition" into "refuted", in exactly the cases D13 and D74 name. D149 gives the opposite outcome for one instance of D72's rule.
- Severity: needs a ruling
- Confidence: medium-high
- What reading dissolves it: D72 applies only when the condition is undecided for lack of information (an input cell), never for lack of effort (limit, opaque predicate); and D149's last sentence is an explicit exception. Then a program's status changes with the budget in one direction only, which D72 should state.

### C10. Order of definition carries no meaning, but a grammar change, an `assert` and a prompt rebinding all act from their position onward
- Decisions: D7 (Order of definition carries no meaning), D88 (A text can change the grammar it is read in), D91 (A grammar change reaches to the end of its block), D96 (Running a program is evaluating its main module with a configuration's capabilities), D97 (Every program is evaluated the same way, however it arrives), D148 (What is known about a value travels with the value)
- Scenario 1: line 2 is `use g`; line 10 is `g = grammar { … }`. By D7 `g` is defined whatever its position. By D88 the parser "evaluates it at once" and "no text is scanned ahead", so at line 2 `g` has no value, the new grammar is unknown, and lines 3–10 cannot be read. Variant: line 1 `x = 1`, line 2 `use make_grammar(x)`, line 30 `x = 2`. D7: the conflict is "reported before either is used". `x` was used at line 2 to parse lines 3–30.
- Scenario 2: the text `x = 1` then `x = 2`. As a module file it is a conflict (D7: "Replacing a definition is an explicit operation"). As two prompt entries it is a silent rebinding (D96). D96 calls a session "a module", and D97 says the same checks apply "however it arrives".
- Scenario 3: `y = Positive(x)` and `assert(x > 0)`, `x` unknown. D148: knowledge holds "after `assert` ... for the rest of the scope". With the assert first, `y`'s claim is decided; with it second, residual. D7 names effects as the only thing with an order, and an assert is a claim.
- Why they conflict: D7 is stated without exceptions other than effects, and three later decisions introduce position-dependent meaning for things that are not effects.
- Severity: needs a ruling
- Confidence: high for scenarios 1 and 2, medium for 3
- What reading dissolves it: D7 governs only the bindings of one closed text after parsing; notation is outside it, a grammar-change form may use only names imported or defined above it, and the prompt is an explicit exception to both D7 and D97. For scenario 3: residual claims are evaluated again when knowledge arrives (D62), so the end state is the same in either order; D148's "for the rest of the scope" then misleads.

### C11. Which effects happen before a refutation depends on evaluation order, and "halts" contradicts "nothing a program does stops the kernel"
- Decisions: D14 (An effect consumes only values whose claims are decided), D63 (The same program and the same information give the same result), D7 (Order of definition carries no meaning), D13 (Claims are evaluated like everything else), D74 (Evaluation stops early for two reasons only), D133 (Nothing is a claim until someone makes it)
- Scenario: a run-phase program: `print("a")`, then an unrelated `verify 1 == 2`, then `print("b")`. D14: "After a phase has refuted a claim, it performs no further effect." The `verify` is independent of both prints. If the evaluator reaches it first, nothing is printed. If it evaluates in written order, `a` is printed. D63: the order in which independent parts are evaluated cannot change the outcome. Separately: D13 "If it comes out false, the phase halts" and D133 "a refuted one halts", against D74 "Nothing a program does makes the kernel stop midway" and D14 "it may go on evaluating to report every refutation". With two independent false claims, a phase that halts at the first reports one of them, chosen by evaluation order.
- Why they conflict: D14's rule is stated in terms of time ("after"), and D63 denies that evaluation time is observable. "Halts" is used in two senses.
- Severity: needs a ruling (the effect ordering); wording (halts)
- Confidence: medium-high
- What reading dissolves it: a phase evaluates every claim that does not depend on an effect's result before performing any effect, and "halts" means "performs no effect and ends refuted". The first part is a scheduling rule the kernel decisions do not state, and it cannot cover claims that depend on run-time input.

### C12. Loaders, prompts and function values need to hold an environment that D56 says no program can hold
- Decisions: D56 (The environment is not a value), D68 (The kernel's primitives are pure and few), D185 (A module is a function of the capabilities it declares), D94 (A module is an extension that arrives as a file), D96 (Running a program is evaluating its main module with a configuration's capabilities), D183 (One kernel serves many invocations), D38 (Functions are data: params plus body), D65 (Substitution of params into bodies), D58 (A call is evaluated by evaluating the function's body)
- Scenario 1: the loader is Allegro code (D94). To load `M` it must evaluate `M`'s expression "in a scope that holds those [capabilities] and nothing else of the kind" (D185), then collect `M`'s bindings to yield an extension. A prompt session handled by Allegro code (D183: "may equally be handled by Allegro code") must keep the bindings of entry 1 and give them to entry 2 (D96). Both need to create a scope, exclude what the ambient scope holds, and read out the bindings an evaluation made. D68 offers only "evaluating an expression with names rebound", which adds names to the current context. Scope creation exists in D174, but that interface is the host's.
- Scenario 2: library `L` has `export f(x) => x + offset`, where `offset` is an input not yet supplied in the check phase. Module `M` has its own `offset = 5` and calls `L.f(1)`. D58 evaluates `f`'s body at the call. D65: substitution "leaves Symbols to resolve by name through the scope". D38: a function is params plus body, with no environment. D56: no value holds one. The symbol `offset` is resolved in the scope current at the call, which is `M`'s, giving 6; or it stays in `M`'s residual as a bare name, and resolves in whatever scope the residual is later evaluated in (D189).
- Why they conflict: both scenarios need a value that stands for "the scope this code was defined or loaded in". D56 forbids it and D38 leaves no place for it.
- Severity: needs a ruling
- Confidence: medium
- What reading dissolves it: for scenario 2, a free name is resolved to its binding (a cell, D61) when the function value is constructed, so a body never holds a bare name; then D65's sentence is wrong and D40's "resolved by base name against the enclosing scope" applies once, at construction. For scenario 1, the kernel has a seventh primitive group: evaluate an expression in a fresh scope given a structure of bindings, returning a structure of the bindings made. That is an environment passed as a structure in both directions, which D56 would have to permit.

### C13. The launcher must fill a cell with an exception, a value only the standard extension can make
- Decisions: D214 (A value that arrives later fills a cell, and a failure fills it with an exception), D19 (Host code reaches a program only as primitive functions), D175 (No interface call writes a bare claim outcome), D105 (The standard language's handled failure is an exception), D73 (A failure a program can handle is supplied by an extension), D212 (The platform's default configuration is the standard language)
- Scenario: a program calls the shipped HTTP capability. The request fails. D214: the launcher fills the cell with an exception. An exception is a value carrying a field the standard extension owns (D105). The launcher is host code: D19 says host code "cannot write metadata", and D175 says "a field an extension owns is never written through the interface". In a configuration without the standard language (D212: the bare kernel, or a domain language whose handled failure is of another kind, D73), the same launcher capability has no exception to produce.
- Why they conflict: D214 gives host code a job that D19 and D175 deny it, and ties a launcher capability to one extension's failure concept, which D73 leaves to each extension.
- Severity: wording
- Confidence: high
- What reading dissolves it: the launcher fills the cell with plain data describing the failure, and a wrapper the standard extension puts around the capability turns that into an exception. D214 should say so.

### C14. Host code may be loaded by code inside an execution, though host code enters only through configuration and nothing exceeds the ceiling
- Decisions: D43 (A capability is granted, never acquired), D181 (Only the launcher sets the ceiling), D186 (Loading is three capabilities of rising strength), D191 (A saved program is a recorded sequence of interface calls), D199 (Three things are trusted: the kernel, the launcher and primitive functions)
- Scenario: the launcher's ceiling is `output` plus the host-loading capability narrowed to one pinned file `fast.js`. Trusted extension `E` loads `fast.js` at run time. D191: the host-code form "can hold primitive functions and even implement a capability". D186: "Host code can do anything". `fast.js` supplies a `sockets` primitive. Code inside the execution now holds a capability the launcher never created. D181: "no code inside can exceed" the ceiling. D43: "host code enters only through the configuration of a phase" and "an extension cannot bring host code of its own". D186 itself implies the opposite default: "A configuration can claim that no host code is loaded after startup."
- Why they conflict: a host-loading capability is unbounded by construction, so a ceiling that contains it is no ceiling, and an extension holding it does bring host code of its own.
- Severity: needs a ruling
- Confidence: medium-high
- What reading dissolves it: the pinned hash list is part of the configuration, so each listed file "entered through the configuration", and the ceiling is defined as the launcher's capabilities plus whatever the pinned files can do. D181's sentence then holds only for configurations that make D186's "no host code after startup" claim.

### C15. "Capability" names things that the phase rules would then withhold: pure arithmetic and module loading
- Decisions: D106 (The core types are built over bits), D46 (Machine arithmetic is a set of pure primitives that ships with the platform), D184 (A capability is a named set of effectful primitives), D144 (An effect is the use of a capability), D157 (Equality, coercion and invariant predicates hold no capability and terminate), D60 (A branch that may not be taken is evaluated without capabilities), D188 (The platform ships three phases: check, run and export), D95 (The loader reaches files through a capability), D88 (A text can change the grammar it is read in)
- Scenario 1: D106: "Integers and floats compute through the machine arithmetic capability". D184: a capability is a set of effectful primitives. D144: "A function that holds none is pure." So `Int.equals(a, b)`, which calls the machine comparison, holds a capability, is not pure, and violates D157. In an undecided branch (D60: "Neither branch is given any capability") `x + 1` would not fold. D46 says the opposite: these are pure and need no grant.
- Scenario 2: `allegro check main.alg`, where `main.alg` starts with `use units`. D188: "Check evaluates a program with no capability to act." D95: "reading a file is an effect" behind a granted capability, and the main file itself is loaded by that loader (D94). With no capability, the read stays residual, the grammar that `use units` yields is unknown (D88), and no line after it can be parsed, so check reports on no claim.
- Why they conflict: one word covers "effectful and granted" in Part II and VI and "pure, shipped" in D106; and "no capability to act" excludes a capability check cannot work without.
- Severity: wording
- Confidence: high for scenario 1; medium for scenario 2 (D213's "files beyond module loading" suggests the authors assume check can read modules)
- What reading dissolves it: D106 means "the machine arithmetic primitives"; and check is granted the module-reading capability, "to act" meaning to change the outside world. Then reading is an effect that some refuted programs still perform, and D14's "no further effect after a refutation" needs the same exception for loading.
